Executive summary

Palimpsest is a mature, disciplined, and genuinely working platform. Across ten independent expert reviews — each grounded in reading the code and probing the live server — every dimension rated “good” health. The 947 backend and 98 frontend tests all pass, and the recent Collections tier (C1–C7) is fully wired end-to-end and demonstrably functional in-browser. Adversarial verification of all high-severity findings refuted none: the issues are real but bounded, concentrated in correctness-honesty of a few statistics/visualizations, event-loop/atomicity robustness for a single-user desktop app, and UX reachability gaps — not systemic architectural failure.

Architecture

Palimpsest layers a genomics analogy over textual analysis: texts are ingested into a Project (with a reversible analyzable/original coordinate map), tracks compute annotation/signal/layer artifacts, an analysis leaf derives statistics, and a collections tier lifts single-text operators to reference-free cross-text corpora. A FastAPI server (77 endpoints) and a React browser (7 tabs) sit on top.

01 Backend architecture & code quality good 3 medium 4 low ▾

The Palimpsest backend is a mature, disciplined codebase with strong architectural bones: a structurally-typed track protocol with dependency-ordered execution, a deliberate atomic-write module, well-documented coordinate-remapping invariants that fail loud, and a genuine shared run path (runner.py) that dedups HTTP and CLI single-track execution. Path/injection validation is thorough and holds up under live probing (traversal returns 403/404, no leak). The main weaknesses are localized rather than systemic: several persisted-and-concurrently-read artifacts bypass the atomic-write module the codebase built for exactly this hazard, several CPU-heavy collections endpoints block the async event loop, and the CLI bulk analyze command re-implements persistence in a way that diverges from the shared writer for layer-keyed tracks. Because the server binds localhost-only for a single-user desktop app, the concurrency/durability gaps are real but bounded in blast radius.

Strengths

  • atomic.py is genuinely crash-safe for the file body: temp file in the same dir + f.flush() + os.fsync() + os.replace(), with temp-file cleanup on BaseException (core/palimpsest/atomic.py:22-39). The module docstring correctly articulates the torn-file / concurrent-poller hazard it defends against.
  • Path-traversal defense is consistent and verified live: _safe_project_dir/_safe_import_path/_safe_gold_map_path all reject '..'/absolute/backslash AND re-check is_relative_to() after resolve() (server.py:631-694); _validate_ids uses a strict ^[a-zA-Z0-9_\-]+$ allowlist (server.py:2706-2710); embedding/chunk labels are hex-validated (server.py:289,338). Live probes on :8092 returned 404/403 for encoded and raw traversal on project_id, embedding label, and /data/{path:path}.
  • The module-scope-BaseModel FastAPI gotcha (silent 422 on function-scoped bodies) is honored: all 17 request/response models are defined at module scope (server.py:28-170), before create_app at line 835.
  • Coordinate correctness is engineered to fail loud, not drift silently: OffsetMap enforces its ordered/disjoint/non-empty span precondition in __init__ (derive.py:33-60); analyzable_text asserts len(text)==omap.child_len before returning (project.py:351-355); remap_signal_data raises UnmappedCoordinateError on an offset-bearing shape it can't handle (derive.py:297,333) rather than mislabeling analyzable coords as original.
  • runner.py successfully removes a whole class of HTTP-vs-CLI drift: extract_masked + persist_track_outputs are the single shared masked-run + persistence path, imported by both the /analyze endpoint (server.py:1306-1311) and the CLI run-track command (cli.py:334-335), and it carries no web-framework dependency so the CLI need not import FastAPI.
  • Type discipline is enforced at the project level (pyproject.toml: [tool.mypy] strict = true), and the server error-handling philosophy is deliberately fail-loud at boundaries — e.g. set_params/validate_params ValueErrors are mapped to clean 400s with the real message (server.py:1279-1293) and the async job records the actual exception type+message rather than a canned label (server.py:1313-1323).

mediumbug◆ groundedPersisted-and-concurrently-read artifacts bypass the atomic-write module, reintroducing the exact torn-file hazard atomic.py was built to prevent
Evidence core/palimpsest/alignment/records.py:88 (write_alignment_records uses open(path,'w')) and :148 (.write_text); core/palimpsest/server.py:2772 (comp_dir/'metadata.json'.write_text non-atomic); core/palimpsest/layout.py:308 (save_layout write_text); core/palimpsest/corpus_graph.py:555 (write_corpus_graph write_text). Each is read by a separate GET endpoint (e.g. read_corpus_graph server.py:2418; alignment_records server.py:2823; load_layout during status polls). atomic.py's own docstring names 'the analysis-status poller reading a manifest while a job rewrites it' as the motivating case.
Recommendation Route these persisted-artifact writes through atomic_write_text/atomic_write_bytes. write_alignment_records and save_layout and write_corpus_graph are the highest-value since each has a paired reader endpoint that can be hit during a rewrite.
mediumperf◆ groundedCPU-bound collections endpoints run synchronously inside async handlers, blocking the single-threaded event loop
Evidence server.py:~2398 build_collection_corpus_graph calls build_corpus_graph() (union-find over all pairwise edges, corpus_graph.py:202-292) + write_corpus_graph() with no asyncio.to_thread; same pattern for phyletic_tree (neighbor-joining O(n^3) distance matrices, corpus_graph.py:392-435) and corpus_analyses (IDF/BM25/clustering, corpus_graph.py:457-527). Contrast run_alignment (server.py:2743-2768) and compute_embeddings (server.py:1561) which correctly wrap heavy work in asyncio.to_thread. A concurrent analysis/status poll stalls until the graph build finishes.
Recommendation Wrap build_corpus_graph / phyletic_tree / corpus_analyses (and their write step) in asyncio.to_thread, matching the alignment/embedding handlers, so a large-collection compute doesn't freeze all other requests.
mediumbug◆ groundedCLI bulk `analyze` re-implements persistence inline and diverges from the shared writer for layer-keyed tracks — latent FR-4 provenance-keying violation
Evidence cli.py:217-229 hand-rolls manifest + write_run_provenance(manifest_dir, name, ...) using the bare track name, instead of calling runner.persist_track_outputs. persist_track_outputs keys layer-keyed tracks (chunking/embedding) by provenance_name()={name}_{label} (runner.py:92,122), so the bulk `analyze` path writes a differently-shaped provenance record than the single-track path (cli.py:335) and the HTTP path (server.py:1311) for the same track. This is precisely the HTTP-vs-CLI divergence runner.py exists to eliminate.
Recommendation Have the bulk `analyze` loop call persist_track_outputs(project_dir, extractor, result) rather than duplicating write_track + write_run_provenance, so all three entry points leave identical on-disk provenance including per-label keying.
lowbug◆ groundedSilent spaCy model fallback: requested model missing → silently substitutes en_core_web_sm, changing analysis results without telling anyone
Evidence core/palimpsest/project.py:52-55 — _load_spacy_model catches OSError and loads 'en_core_web_sm' unconditionally. spacy_doc defaults to 'en_core_web_lg' (project.py:243) and pipeline_run records spacy_model as en_core_web_lg (cli.py:257), so provenance can claim _lg while entities/syntax actually ran on _sm. This is a silent-fallback-masking-missing-data pattern the project explicitly rejects ('Fallbacks Are Failures').
Recommendation Either fail loud when the requested model is absent, or record the actually-loaded model name in provenance so pipeline_run.json doesn't misattribute the model.
lowbug◆ groundedload_layout swallows OSError from its persisted backfill, silently discarding the one-time parent-computation work on any write failure
Evidence core/palimpsest/layout.py:300-303 — after backfilling parent_id and setting parents_computed=True in memory, save_layout is wrapped in try/except OSError: pass. If the save fails (disk full, permissions), the in-memory cfg is still returned as if persisted, so the O(n^2) backfill re-runs every load and no error is surfaced.
Recommendation Log at minimum, or let the OSError propagate; combined with making save_layout atomic this becomes a clean fail-loud path.
lowbug◆ groundedatomic_write_bytes fsyncs the file but not the parent directory after os.replace — the rename can be lost on a crash even though the file body is durable
Evidence core/palimpsest/atomic.py:28-32 fsyncs the temp file fd, then os.replace(tmp, path) at line 32, but never opens+fsyncs path.parent. On most filesystems a crash immediately after os.replace can leave the directory entry pointing at the old (or no) inode. For a local desktop app this is a minor durability gap, not a correctness-under-normal-operation bug.
Recommendation After os.replace, open the parent dir with os.open(dir, O_DIRECTORY) and os.fsync it (best-effort, ignore ENOTSUP) to make the rename itself crash-durable, completing the guarantee the module docstring implies.
lowdesign◆ groundedAll job/run state is in-memory module-level dicts — lost on server restart, leaving completed/failed runs invisible and no cross-process coordination
Evidence server.py:25 _job_semaphore=asyncio.Semaphore(3); _running_jobs / _alignment_jobs are plain dicts populated at server.py:1301,1319,1554,2724,2782. A completed run's status is only knowable for 30–60s (call_later cleanup at :1325,:1575,:2787) then reconstructed from disk existence; a mid-run restart drops the 'running' marker and any error message. The already_running guard (e.g. server.py:1211) is per-process only.
Recommendation Acceptable for the current localhost single-process desktop deployment, but if multi-worker/uvicorn --workers is ever used the guards break silently. Document the single-worker assumption, or persist job state (the run.json provenance already exists as a durable anchor).
02 API contract & endpoint integrity good 2 medium 4 low 1 info ▾

The 77 HTTP endpoints in server.py are well-disciplined: OpenAPI reports exactly 77 operations across 70 paths (matching the documented count), error codes are consistent and semantically correct (400 bad-request, 404 missing, 409 metric-congruence), path-traversal is blocked, and the SSE streaming and metric-congruence-gated endpoints are exemplary. Live probes of :8092 all passed: congruence returns all_congruent=true for both cosine and word_overlap, bad metric yields 400, missing collection yields 404, and matrix.bin byte-count matches the manifest dimensions exactly. The two real weaknesses are (1) a binary wire-contract that is inconsistently self-describing across the four .bin endpoints, and (2) substantial HTTP/CLI drift — the claim that cli.py mirrors all endpoints is false: the entire Wave-0 per-project analysis surface and alignment run/diff operations are HTTP-only.

Strengths

  • Congruence contract is fully correct on the live server: GET /api/collections/matthew-mark-validation/congruence?metric=cosine returns all_congruent=true with needs_embedding=true and per-member congruence keys (embedding:cosine:c9757c16...); ?metric=word_overlap returns all_congruent=true needs_embedding=false; ?metric=BOGUS returns HTTP 400 with 'unknown similarity metric(s): BOGUS; valid metrics: cosine, jaccard, word_overlap, edit_distance'; missing collection returns HTTP 404 'Collection not found' (server.py:2378-2394).
  • Metric-congruence gating is a genuine architectural strength: the probe endpoint (server.py:2472-2522) maps MetricCongruenceError->409, KeyError->404, ValueError/FileNotFoundError->400, and enforces mutual-exclusion validation (exactly one of 'q' or 'ref_project'+'ref_chunk', else 400). Sweep mirrors the same 409 gating (server.py:2542).
  • Binary matrix contract is internally consistent where it counts: live matrix.bin returned exactly 12,222,012 bytes and the sibling /matrix JSON manifest reports dimensions [1747,1749], dtype float32, byte_order little-endian — 1747*1749*4 = 12,222,012, a byte-exact match, and _f32_le_bytes serializes as '<f4' C-order (server.py:314-317).
  • SSE streaming endpoints are robust: /import/local/stream and /derive/stream (server.py:2025-2086, 2211-2278) run ingest/derive in a worker thread, marshal progress via loop.call_soon_threadsafe into an asyncio.Queue, emit terminal done/error events carrying the real HTTP status in the payload, and set Cache-Control:no-cache + X-Accel-Buffering:no for proxy-safe streaming.
  • Error-code and traversal discipline verified live: missing alignment records -> 404 'No alignment results found', missing project analysis/status -> 404 'Project not found', encoded traversal (..%2F..%2Fetc) -> 404 (route-level rejection); _safe_project_dir and serve_project_file both reject '..','/','\\' and enforce is_relative_to(workspace) (server.py:631-640, 2961-2974).

mediumdesign◆ groundedBinary wire-contract is inconsistently self-describing: matrix.bin, /lane, and /projection ship NO shape/dtype header while /heatmap does
Evidence GET /api/alignment/{q}/{t}/matrix.bin returns raw application/octet-stream with headers date/server/content-type/accept-ranges/content-length/last-modified/etag but NO X-Matrix-N, dtype, or byte_order — the shape lives ONLY in the separate /matrix JSON manifest (server.py:2930-2937). /lane (server.py:1728) and /projection (server.py:1632) also return bare Response(content=_f32_le_bytes(...)) with no shape header. Only /heatmap sets X-Matrix-N/X-Matrix-Reduced/X-Matrix-Order (server.py:1686-1691). So one binary family self-describes via headers, another relies on an out-of-band JSON fetch, and lane/projection rely on byteLength/4 inference.
Recommendation Standardize a minimal binary header on every .bin endpoint: X-Matrix-N (and X-Matrix-Cols for N×2/N×M), X-Dtype: float32, X-Byte-Order: little-endian. This makes matrix.bin decodable without the coupled /matrix fetch and lets clients validate rather than infer.
lowbug◆ groundedFrontend trusts little-endian blindly and never validates the manifest byte_order it fetches
Evidence comparisonStore.ts:163-169 fetches the /matrix manifest AND matrix.bin, then does `new Float32Array(buffer)` — which uses the host's native endianness (LE on x86/ARM in practice) and ignores the manifest's byte_order:'little-endian' field entirely. LayerLane.tsx:104, EmbeddingScatter.tsx:27, and DotplotView.tsx:300-314 likewise do `new Float32Array(buf)` with no header/endianness check (grep for headers.get in these files returns nothing). The contract is correct today only because _f32_le_bytes always writes '<f4' and all target platforms are LE.
Recommendation Either assert manifest.byte_order==='little-endian' on the client and throw loudly otherwise, or drop byte_order from the manifest as a false-promise field. A silently-ignored contract field is worse than none.
lowbug◆ groundedNon-streaming /derive does not map FileExistsError to 409, unlike its /derive/stream sibling and the import endpoints

Recommendation Add `except FileExistsError: raise HTTPException(409, 'Project already exists')` to both /derive and /derive/stream so a name collision is a conflict, not a server error, matching the import contract.

03 Frontend / UI code quality & architecture good 4 medium 5 low ▾

Palimpsest's single-text journey (import → sections → tracks → reading/browser/analysis/dotplot) and the collections workbench (Compare, Corpus with Overview/Members/Corpus/Masking/Analyses/Sweep/Probe) are genuinely mature and mostly complete, with strong empty/loading/error states and an unusually disciplined cost-confirmation culture in the collections tier (Probe, Sweep, Reconcile all gate expensive work behind a CostDialog and never auto-run).
