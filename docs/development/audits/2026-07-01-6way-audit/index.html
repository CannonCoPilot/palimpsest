Executive summary

Palimpsest is a mature, disciplined, genuinely working platform — the ingestion→tracks→analysis→collections stack is coherent, fail-loud where it matters, and the recent KJV verse-paragraph fix is verified end-to-end (Geneva↔KJV Matthew aligns as one clean 1071×1071 diagonal). But unlike a surface pass, this expanded 6-way audit deliberately stress-tested the cross-text analytics with a corpus whose ground truth is known — three translations × two gospels — and that pressure surfaced real, bounded issues. Across 14 independent expert dimensions, health lands at 9 good · 4 fair · 1 concerning. Of 109 findings (4 critical, 27 high), every one of the 31 adversarially-verified critical/high findings held up — 24 confirmed, 7 scoped to partial, 0 refuted. The issues concentrate in three places: cross-text similarity correctness (an unthresholded word-method graph merges Matthew and Mark; the phyletic tree contradicts the known translation structure), API/data-path integrity (an embedding-DB path split breaks the default semantic alignment), and visualization honesty (unlabeled color scales, indistinguishable member names). None are systemic architecture failure; all are addressable, and the 6-way corpus now makes each one measurable.

Methodology

A divide-and-conquer fleet of 45 expert agents each owned one slice of the system and produced findings grounded in file:line evidence, an observed API response, or a captured screenshot. The six UI dimensions operated under an explicit visual-integrity mandate: not merely “did the page render,” but “does every analysis generate tracks that render, is every plot interactive enough to navigate and explore, and is the data shown useful, honest, and methodologically correct?” Every critical/high finding was then handed to an independent adversarial verifier instructed to refute it (31 verified across two verification passes). All live probing hit an isolated server on :8092 serving the embedded 6-way collection; the shared human session on :8080 was never touched.

The 6-way validation corpus — a known-answer stress test

The audit substrate is deliberate: three English translations of the Bible — the Catholic Douay-Rheims (2018), the Protestant 1599 Geneva, and the King James (1611/1769) — each reduced to two gospels, Matthew and Mark, giving six single-book subtexts in one collection. Because the relationships among these six are known a priori, they form a ground-truth harness for Palimpsest's data handling, alignment, statistics, and visualization.

Geneva and KJV share a versification and near-identical wording (strong true-positive signal); Douay-Rheims follows the Vulgate and drifts by a verse in places (a controlled alignment-robustness test); Matthew vs. Mark is the synoptic case — related content, different wording (the hard cross-book case).

What each comparison tests

  • Gen·Mt × KJV·Mt — baseline translation-equivalence; should be one clean diagonal (it is: score 519, single record).
  • DR × Geneva (same book) — versification-drift robustness; fragments correctly at the +1 shift.
  • Matthew × Mark — synoptic parallels; the hard case where word-overlap is weak and embeddings should help.
  • All six together — reference-free pangenome “core/shell/singleton,” Circos ribbons, phyletic tree.
This known-answer design is also what exposed the sharpest defects: the corpus-graph merge, the phyletic mis-clustering, and the fact that the rigorous synoptic TP/TN oracle is not yet wired into a precision/recall number.

Architecture

Palimpsest layers a genomics analogy over textual analysis: texts are ingested into a Project (with a reversible analyzable/original coordinate map), tracks compute annotation/signal/layer artifacts, an analysis leaf derives statistics, and a collections tier lifts single-text operators to reference-free cross-text corpora. A FastAPI server (77 endpoints) and a React browser (7 tabs) sit on top.

01 Backend architecture & code quality good 2 high 5 medium 3 low ▾

The backend is a mature, thoughtfully-engineered codebase: leaf packages (atomic.py, runner.py, derive.py/OffsetMap, tracks/registry.py) are cohesive, fail-loud, and correct, with rich docstrings that record the reasoning behind past bug fixes. The dominant structural weakness is server.py: a 2989-LOC module whose create_app is a single ~2150-line function holding all 77 endpoints as closures, and — critically — the one place in the codebase that bypasses atomic.py. Every track/CLI/runner path writes atomically, but server.py (0 atomic references) and derive.py/layout.py's save_layout truncate-in-place on load-bearing files (layout_sections.json, annotation tracks, character cache, alignment metadata), reintroducing the exact C3 torn-read and C1 missing-provenance classes the atomic/runner refactors were built to eliminate. The KJV verse-paragraph fix is verified correct and reflected end-to-end (1071==1071 on disk; clean full-length diagonal in the dotplot viz).

Strengths (6)

  • atomic.py is textbook-correct: temp-file-in-same-dir + f.flush() + os.fsync() + os.replace(), with BaseException cleanup of the temp file (atomic.py:22-39). runner.py, cli.py, and all 8 track modules consistently route writes through it.
  • runner.py is a model of separation-of-concerns: it exists specifically to share the masked-run path between HTTP and CLI (runner.py:4-9), has no web-framework dependency so the CLI imports it without FastAPI, and _remap_signal_dir fails LOUD via UnmappedCoordinateError rather than writing analyzable coords mislabeled as original (runner.py:39-43).
